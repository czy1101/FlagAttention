# GLA-002 final report: FP16 backward-state parallelism for 64x64 GLA

## Verdict
The experiment **supports modifying PR #42**: enabling the FP16 parallel
backward-state path strictly for `K=V=64` passed the existing recurrent-reference
test and a direct comparison with PR #42's code (max relative RMS 1.34e-6,
no NaN/Inf). An independent reviewer's same-input, alternating-process A/B
measured **8.665 ms → 2.255 ms (3.84x)** for T512 FP16 forward+backward.
The result does **not** justify broadening FP16 beyond 64x64; BF16 dispatch is unchanged.

## Change
`src/flag_attn/runtime/backend/_enflame/FLA/chunk_h.py`, function `chunk_bwd_dh`
only. The three hard `== torch.bfloat16` dtype checks become:

    and (k.dtype == torch.bfloat16
         or (k.dtype == torch.float16 and K == 64 and V == 64))
    and q.dtype == k.dtype
    and do.dtype == k.dtype

Every other precondition is untouched (PARALLEL_STATE_ENABLED,
PARALLEL_BWD_STATE_ENABLED, cu_seqlens is None, BS==BT==64, HQ==H,
not state_v_first, g/g_gamma/gv None, gk not None). For BF16 the predicate is
logically identical to the original, so BF16 takes exactly the same path.
FP16 is admitted **only** at K=64 and V=64; 64x128, 128x128 and 32x32 continue
to use the fallback. The forward path and PR #42's forward change are untouched.

## Steady-state timing: exact candidate versus PR #42 (reviewer correction)
The reviewer used two isolated clones of `7ac4406`. The candidate clone differs
only by the 12-line backward dtype gate shown above. Both use the default
`PARALLEL_BWD_STATE_ENABLED=True`. The same `bench.py` input and wall-clock timing
method ran on `gcu:0`, with 3 alternating baseline/candidate processes. Each
process warmed 3 calls and timed 5 synchronized forward+backward calls. The
per-process median values were:

| round | PR #42 baseline (ms) | candidate (ms) |
|---|---:|---:|
| 1 | 8.665 | 2.316 |
| 2 | 8.687 | 2.195 |
| 3 | 8.609 | 2.255 |
| median | **8.665** | **2.255** |

The median-of-round-medians speedup is **3.84x**. Raw process logs are in
`agent-results/reviewer-ab/`. This is host wall time with explicit GCU
synchronization, after compilation; it is not a device-event kernel-only result.

The agent's earlier `alt.py` comparison toggled
`PARALLEL_BWD_STATE_ENABLED`. That flag changes both the backward-state path
and forward-state recomputation during backward, so those measurements do not
isolate this code change. The agent script also used an upper-middle value for
six samples rather than the statistical median. Its raw samples are retained
as diagnostic data but its reported 1.96x is superseded by the direct A/B above.

The reviewer also ran `correct.py` on the two exact clones with the same seed
and inputs: output, final state, dq and dv matched at recorded precision; dk
relative RMS was 5.57e-7, dg 1.34e-6, and dh0 1.33e-7. All finite, both
processes exited 0. See `agent-results/reviewer-ab/candidate-correct.log`.

## First-compile vs steady state
Candidate T512 FP16 fwd+bwd including cold Triton compile: 71s, exit 0 in the
agent run. Reviewer warm steady state was 2.2-2.3 ms on its two-clone harness;
the different timing setup should not be mixed with agent toggle samples.
Cold-compile numbers are **not** used to infer any speedup.

## Passed scope / unverified scope
Passed: FP16 and BF16, K=V=64, BT=BS=64, no cu_seqlens, HQ==H, T=64 and T=512,
g/g_gamma/gv None, gk present, including PR #42's T512 FP16 case and the T63
FP16 regression.
Unverified: K or V != 64 (deliberately not enabled), T > 512, HQ != H (GQA),
cu_seqlens/varlen, state_v_first, split_size != chunk_size, g_gamma/gv set,
different gate_logit_normalizer for FP16 beyond the existing tests, and
multi-device. The 128x128 and 64x128 rows above were executed but stay on the
fallback path, so they say nothing about a parallel path at those sizes.

## Limitations
- Only one machine / one GCU generation; timings are not portable.
- The agent sweep used 3 toggle measurements per point; it cannot attribute
  performance differences to the candidate code alone. The reviewer A/B used
  3 alternating process pairs, each with 5 warmed calls.
- GCU 1 was present in the container and visible to torch; it was never used by
  this work, but the container does not support masking it off via
  GCU_VISIBLE_DEVICES. All allocations went to gcu:0.

## Recommendation
Worth folding into PR #42 as a separate commit: it is a forward-mirroring gate
change, keeps BF16 dispatch identical, passes the target correctness test, and
improves the exact PR-baseline comparison 3.84x at T512 FP16 64x64 in the
reviewer harness. T64's incremental code-delta speedup remains unmeasured.
Do not extend FP16 to other dimensions without separate measurements.
