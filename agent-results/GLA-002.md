# GLA-002 final report: FP16 backward-state parallelism for 64x64 GLA

## Verdict
The experiment **supports modifying PR #42**: enabling the FP16 parallel
backward-state path strictly for `K=V=64` is numerically equivalent to the
fallback (max rel. RMS ~2.5e-6, no NaN/Inf) and is ~2.0x faster at steady state
on the PR #42 target case. The gain does **not** generalize beyond 64x64, so the
FP16 gate must not be broadened. BF16 behaviour is unchanged.

## Change
`src/flag_attn/runtime/backend/_enflame/FLA/chunk_h.py`, function `chunk_bwd_dh`
only. The three hard `== torch.bfloat16` dtype checks become:

    and (k.dtype == torch.bfloat16
         or (k.dtype == torch.float16 and K == 64 and V == 64))
    and q.dtype == k.dtype
    and do.dtype == k.dtype

Every other precondition is untouched (PARALLEL_STATE_ENABLED,
PARALLEL_BWD_STATE_ENABLED, cu_seqlens is None, BS==BT==64, HQ==H,
not state_v_first, g/g_gamma/gv None, gk not None). For BF16 the predicate is
logically identical to the original, so BF16 takes exactly the same path.
FP16 is admitted **only** at K=64 and V=64; 64x128, 128x128 and 32x32 continue
to use the fallback. The forward path and PR #42's forward change are untouched.

## Steady-state timing (fwd+bwd, same input, same device, alternated)
Toggle is read at call time, so fallback/candidate were alternated within one
process after warming both branches (`agent-results/alt.py`). FP16 T512 64x64,
3 rounds x 2 measurements each:

    candidate ms: 15.06, 14.75, 16.10, 15.07, 12.02, 12.40  (median 15.06)
    fallback  ms: 29.46, 31.07, 27.76, 27.20, 30.42, 26.90  (median 29.46)
    speedup 1.96x (all 6 paired comparisons faster on candidate)

## Dimension sweep (1 round-pair x 3, median of 3; `agent-results/sweep.py`)
| dtype | T | K | V | cand ms | fall ms | speedup | o max_abs |
|---|---|---|---|---|---|---|---|
| fp16 | 64  | 32  | 32  | 5.94  | 5.95  | 1.00x | 0.0 |
| fp16 | 64  | 64  | 64  | 3.50  | 4.69  | 1.34x | 0.0 |
| fp16 | 512 | 64  | 64  | 14.17 | 29.54 | 2.08x | 0.0 |
| fp16 | 512 | 64  | 128 | 53.02 | 53.85 | 1.02x | 0.0 |
| fp16 | 512 | 128 | 128 | 98.91 | 92.87 | 0.94x | 0.0 |
| bf16 | 512 | 64  | 64  | 19.28 | 40.07 | 2.08x | 0.0 |

Interpretation: 32x32, 64x128 and 128x128 show ~1.0x because neither path enters
the parallel specialization there (forward gate already requires K=V=64), so those
rows only confirm that the candidate does not perturb non-64x64 shapes. The real
benefit is 64x64 only. 128x128's 0.94x is within run-to-run noise on an
already-fallback path, not a regression attributable to the change.

## First-compile vs steady state
Candidate T512 FP16 fwd+bwd including cold Triton compile: 71s, exit 0.
Warm steady state is 12-16 ms. Cold-compile numbers are **not** used to infer
any speedup.

## Passed scope / unverified scope
Passed: FP16 and BF16, K=V=64, BT=BS=64, no cu_seqlens, HQ==H, T=64 and T=512,
g/g_gamma/gv None, gk present, including PR #42's T512 FP16 case and the T63
FP16 regression.
Unverified: K or V != 64 (deliberately not enabled), T > 512, HQ != H (GQA),
cu_seqlens/varlen, state_v_first, split_size != chunk_size, g_gamma/gv set,
different gate_logit_normalizer for FP16 beyond the existing tests, and
multi-device. The 128x128 and 64x128 rows above were executed but stay on the
fallback path, so they say nothing about a parallel path at those sizes.

## Limitations
- Only one machine / one GCU generation; timings are not portable.
- Sweep used 3 alternated measurements per point (FP16 T512 64x64 had 6),
  so ~1.0x rows cannot exclude small (<5%) effects.
- GCU 1 was present in the container and visible to torch; it was never used by
  this work, but the container does not support masking it off via
  GCU_VISIBLE_DEVICES. All allocations went to gcu:0.

## Recommendation
Worth folding into PR #42 as-is: it is a 9-line, forward-mirroring gate change,
keeps BF16 bit-identical, passes all targeted correctness tests, and gives ~1.3x
at T=64 and ~2x at T=512 for FP16 64x64. Do not extend FP16 to other dimensions
without separate measurements.
